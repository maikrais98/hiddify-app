# Согласованный объём диагностики для объединения с текущими исправлениями Blizzard

24 октября 2026. Пользователь одобрил этот объём («Ок») и поручил объединить его с соседним чатом. Чат-получатель: «Проверь логи подписки». Рабочий код в исходном чате диагностики не менялся; переносить коммиты нечего.

Этот документ заменяет рекомендуемую архитектуру первоначального проекта `2026-10-24-expanded-diagnostics-design.md`. Исходная большая схема была упрощена после обсуждения. Приоритет пользователя: сохранить качество и точность, переиспользовать существующие механизмы, native API и компоненты, без переписывания.

## Что объединить

1. Подписки: ручной/автоматический update и import, вход действия, скачивание, вложенные remote lines (агрегированно), metadata/parse, changeOptions, validate_and_commit_config, DB persist, решение о reconnect и его фактический результат. Один диагностический контекст попытки. Нынешний validateConfigByPath совмещает проверку и запись конфигурации — раздельные успехи выдумывать нельзя. Partial nested failure наблюдать без изменения бизнес-поведения.
2. Существующий HTTP-клиент Dio: типизированный исход/категория, HTTP status или закрытый код статуса, выбранный режим direct/proxy/both, ограниченные сведения о повторах. Это выбранный режим, не доказанный реальный маршрут fallback. Не заменять Dio на URLSession. Не выводить URL, requestOptions, headers, body, конфиги или error.toString. Общий connectionError не объявлять DNS/refused без подтверждающего типизированного источника.
3. Подключение: сохранить нынешние observers и lifecycle/ping trace; дополнить готовность/применение options/background start/результаты, ignored/skipped и связь update→reconnect. Диагностика не добавляет reconnect, не меняет Connected guard, manual OFF, таймауты или выбор сервера.
4. Native: сохранить полный NEVPNStatus в диагностике до текущего UI-маппинга: connecting отдельно от reasserting, invalid отдельно от disconnected. Проверять принадлежность уведомления нашему connection без вывода идентификаторов; текущий NotificationCenter observer подписан с object:nil. UI-поведение не менять побочно.
5. Native: записать уже доступный NEProviderStopReason, получение sleep/wake callbacks, начало/итог существующего setTunnelNetworkSettings, получение TUN descriptor (факт/ветка, без descriptor value), этапы preferences load/save/reload, исходные разрешённые NSError domain-category/code до схлопывания в строку/общий code 0. NSError description/userInfo/произвольный domain не передавать. Событие возврата MobileWake не означает восстановление интернета.
6. Небольшое дополнительное Apple API: fetchLastDisconnectError, доступен с iOS 16 (проверено в установленном SDK). Availability guard, nil/unknown, корреляция с последним отключением; не приписывать старую ошибку новой попытке. Ответ может быть ошибкой от extension, а не системной первопричиной. Нормализовать по allowlist.
7. Доставка: использовать SafeDiagnosticJournal → существующий BetterStackLogPrinter/outbox → Better Stack и текущий SafeDiagnosticsPage. У outbox уже есть persist-before-send, restore, retry, TTL, budget и HTTP receipts. Не строить второй sender или новый backend. Native подключить через существующий Flutter/native bridge и существующий безопасный журнал, сохранив прошлый эпизод между переподключениями. Если для корректного импорта нужен стабильный source key и durable handoff — добавить минимальный подтверждённый тестами механизм в нынешний outbox, а не терять cursor до сохранения.
8. Размеры и схема: предыдущие 4096/2 МиБ и новая большая event-v2 модель не являются согласованной обязательной реализацией. Расширять текущие closed enums/строгую модель только необходимыми полями; сначала измерить объём. Бюджет 5 МиБ/UTC-сутки уже в build25 — повторно увеличивать не надо. Совместимость сохранённой очереди и analytics OFF обязательны. Пропуски/переполнение/storage failure показывать явно, без обещаний exactly-once.

## Границы

- Дополнительные NWPathMonitor/активные DNS-HTTPS probes/packet capture/новые сервисы и переписывание core в текущий объём не входят.
- Статус OS connected, core started, URL-test и прохождение внешнего трафика — отдельные факты. При отсутствии причины показывать unknown, не диагноз по предположению.
- Уже найденные проблемы cleanup temp, старого profile object и поведения background reconnect не исправлять попутно. Если есть уже отдельно авторизованное исправление foreground_settings_unavailable в принимающем чате — интегрировать с ним и переиспользовать его типизированные результаты.
- Эта координация не даёт новой авторизации на signing/upload/install/device mutation. Существующие разрешения принимающего чата проверять по его человеческим сообщениям.

## Проверки и объединение

Сначала RED-тесты для каждого добавленного этапа/исхода, затем минимальная production-реализация, GREEN и применимые регрессии. Проверить сохранение исходных результатов/исключений/порядка/ленивости операций, native callback semantics, связь попыток, privacy canaries, queue restore/offline/restart/ошибки записи/analytics OFF. Нужна проверка обеих iOS targets. Физический traffic acceptance отдельно от тестов и доставки.

Принимающий чат объединяет диагностику с его текущими UI-исправлениями в общий план/кандидат, с отдельными проверяемыми блоками и без пересечения правок. Исходный чат диагностики не начинает параллельную реализацию. Текущая изолированная копия UI по прочитанному состоянию — `blizzard-physical-ui`; актуальную ветку, HEAD и dirty state перепроверить перед объединением.
