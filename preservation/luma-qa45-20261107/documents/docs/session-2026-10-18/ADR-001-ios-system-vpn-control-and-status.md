# ADR-001: ручное управление VPN и системный статус iOS

Дата: 18 октября 2026. Статус: **принято и реализовано в поставках7–9**. Основной сценарий сборки9 принят пользователем; полная сетевая/lifecycle-матрица отдельно не принята. Документ описывает выпущенный source `9e6f3167af0c913c54c549ef5bc38f5bfd7169e2`, а не draft PR26.

## Контекст

Пользователь выбрал WIR Baseline и потребовал управлять VPN из приложения и системных настроек. Выключение через iOS вызывало немедленное переподключение. Позднее VPN включался снаружи, но WIR показывал устаревший статус; перезапуск приложения восстанавливал его. У native-состояния iOS, gRPC-состояния Core и отображаемого текста разные источники и время обновления. Пропадание канала наблюдения не равно остановке туннеля; Connected не равно доказанному рабочему трафику.

Доказательства: manual-policy RED/GREEN; интеграционный RED с настоящими production MobileCore/service, fake EventChannel и локальным gRPC; диагностика закрытыми кодами/enum; пользовательские наблюдения. Причина отдельной ранней неудачи внешнего запуска на build8 не была доказана.

## Решение

1. **Ручной режим по умолчанию для этого сценария.** Перед явным подключением сохранять `isEnabled=true`, `isOnDemandEnabled=false`, пустые `onDemandRules`. Старое Connect On Demand очищается через существующий путь подключения из WIR. Settings OFF не должен сам превращаться в новый запрос подключения. Это решение введено до build9.
2. **Ошибки системных preferences/start возвращать вызывающему коду.** При невозможности сохранить ручную политику не продолжать start. Повторная осознанная попытка остаётся возможной. Диагностика передаёт стабильные коды без системного текста и параметров профиля. Реализовано в build8.
3. **На iOS источником состояния системного туннеля являются native events и свежий системный snapshot.** Доставлять события в существующий service/statusController. Обычный запоздалый gRPC Starting/Started/Stopped и завершение listener не перезаписывают уже авторитетное системное состояние. CoreStopped с alert сохраняет диагностическое значение.
4. **Упорядочивать события и жизненный цикл.** Подписка на native state создаётся один раз на Core instance; service восстанавливает наблюдение после pause/resume. Счётчик revision защищает более новое событие от старого асинхронного snapshot. Закрытие foreground-наблюдения не останавливает системный VPN и не фабрикует OFF.
5. **Отделить app-driven startup.** Пока команда запуска кнопкой WIR не завершена, промежуточные native-состояния откладываются. При успехе публикуется актуальное состояние; при отсутствии события выполняется защищённый refresh. Ошибка Core во время запуска не стирается отложенным Started. Ошибка финального чтения передаётся в error-поток. Не показывать успех только из-за раннего события.
6. **Ограничить новый арбитраж iOS capability.** Android/desktop сохраняют существующий gRPC-путь. Для non-iOS проверена последовательность transient error→Started во время незавершённого start RPC.
7. **Сохранять различие state и reachability.** Системный статус сообщает состояние VPN-сессии. Успешная команда, наличие процесса или Connected не считаются измерением DNS/TCP/UDP/маршрута. Продуктовая Home-ветка, которая показывает Connecting при Connected с неизвестной latency, не исправлена этим ADR/патчем и остаётся отдельным предметом QA.

## Рассмотренные альтернативы

| Альтернатива | Почему не выбрана |
|---|---|
| Оставить безусловный Connect On Demand | Противоречит требованию ручного OFF; пользователь воспроизвёл переподключение |
| Исправить только надпись или требовать перезапуск WIR | Не устраняет потерю живых системных событий; перезапуск — симптом, а не контракт |
| Читать snapshot только при открытии/resume | RED воспроизвёл потерю поздних Stopped/Started при недоступном gRPC |
| Просто объединить native и gRPC | Не определяет приоритет и порядок; старый ответ может перетереть новый, ранний Started — скрыть ошибку запуска |
| Считать закрытие gRPC признаком OFF | Наблюдение может исчезнуть при рабочем системном туннеле |
| Скрыть все Core alerts после native Started | Теряются реальные диагностические ошибки |
| По гипотезе заменить Core, добавить watchdog или изменить threading/TUN | Для причины внешнего запуска нет достаточного runtime-доказательства; проверенный конфиг имел `hasTunInbound=true` |

## Последствия и ограничения

- Settings/Control Center и WIR используют единый источник состояния iOS; пользовательское ручное выключение сохраняется. Нужна однократная миграция старой On Demand-политики через подключение из WIR.
- Добавлена сложность порядка асинхронных событий. Она покрывается регрессиями: late native events, stale snapshot/gRPC, повторный setup, pause/resume, app-start failures и alerts, final-refresh error, non-iOS path.
- Ошибки чтения остаются видимыми; не подменяются ложным OFF/Connected.
- Автоподключение в будущем должно быть отдельным явным режимом со своим контрактом и приёмкой, а не скрытым возвратом старого поведения.
- В build9 не менялись Swift, Core, DNS, routing или On Demand. Ранее принятые Swift/On Demand-изменения остаются частью baseline.
- Принятие пользователя относится к внешнему переключению и возврату без перезапуска. Симптом после sleep/unlock из параллельного QA нельзя объявлять исправленным. Сначала нужны одновременно системное состояние и UI; участие latency-ветки пока гипотеза.
- Draft PR26 об обработке `changeOptions` — независимое, ещё не выпущенное изменение. Его CI-блокер и собственная приёмка не закрываются этим ADR.
