# Ревью плана развития Luma: меньше новой системы, больше готового Hiddify

Дата: 8 ноября 2026 года. Проверенный код: PR #75, HEAD `9a15af24fc838190525d80370493ec546a7a2ec1`. PR уже слит; GitHub compare с merge commit `93de6d7220026a33271a4e568e5587b1d8224f8d` не содержит изменений файлов.

**Вывод:** первоначальный план хорошо разделяет доказательства и защищает выпуск, но как ближайшая очередь работ слишком широк. Следует оставить три результата: приёмка новой базы, кабинет с email/Telegram и получением подписки, понятный первый сеанс/восстановление. Визуальная проверка, тесты и диагностика сопровождают эти результаты, а не становятся отдельными большими проектами.

Изменения внесены в [Plan.md](../Plan.md). Код приложения не менялся; тесты и устройство не запускались. Это ревью по исходникам, не новый отчёт об исправленных runtime-багax.

## Оценка с разных сторон

| Сторона | Что было хорошо | Что требовало пересмотра | Решение |
|---|---|---|---|
| Пользовательская польза | Первый сеанс, ошибки, сохранность данных | Кабинет отложен вместе с оплатой, хотя нужны показатели и выбранный вход | Самостоятельный D0 с email/Telegram и получением подписки; оплата отдельно |
| UX | Сохранение Luma и доступности | Полный каталог экранов и зависимость функций от большого визуального этапа | Проверять изменяемые пути; не добавлять третью вкладку по умолчанию |
| Архитектура | Сохранение официального runtime | Недостаточно точный договор о квоте, скорости, периодах и refresh | Переиспользовать модели/actions с явными границами отображения |
| Надёжность | Signed/physical проверки не заменяются симулятором | Одни проверки выглядят как несколько проектов A/F1/F5 | Один пакет приёмки по SHA и артефакту |
| Стоимость сопровождения | Минимизация отличий от upstream | Слишком много параллельных P1: CI, метрики, диагностика, реестры | Расширять существующие инструменты по мере затронутого риска |
| Приватность и аккаунты | Отправка диагностических данных требует понятного договора | Импортированный профиль можно ошибочно принять за подтверждённый аккаунт | Разделить просмотр профиля и серверный вход; не переносить admin API в приложение |

## Существенные находки и принятые исправления плана

### 1. Авторизация включена в первую версию, оплата отделена

Модель `RemoteProfileEntity` уже несёт название, время обновления и `SubscriptionInfo`; экран деталей показывает расход/лимит/срок. Эти механизмы можно переиспользовать для отображения и импорта, но выбранный пользователем вход требует серверного пользовательского API и сессии. Сам экран деталей — редактор, поэтому целиком переносить его в кабинет не стоит.

Источник: `lib/features/profile/model/profile_entity.dart:17`, `lib/features/profile/details/profile_details_page.dart:230`.

**Решение пользователя от 8 ноября:** вход через email/Telegram и получение подписки включены в D0. Рекомендация ограничиться локальным обзором не принята и больше не является планом первой версии. Добавлены проверка существующего API, оба способа входа, сессия, связь серверной подписки с профилем Hiddify и выход. Оплата/HWID/web-кабинет остаются за пределами первой версии. Старый вход по знанию телефона/логина заменён подтверждёнными email/Telegram.

### 2. Переиспользование не означает копирование семантики вслепую

`SubscriptionInfo` — данные провайдера. `SystemInfo` — текущая статистика работающего core. Накопленные байты core не подтверждают расход тарифа за месяц или со всех устройств. `remainingBW` может быть отрицательным; parser нормализует некоторые отсутствующие значения. `StatsNotifier` при ошибке возвращает пустую статистику.

Источники: `lib/features/profile/model/profile_entity.dart:55`, `lib/features/profile/data/profile_parser.dart:293`, `lib/features/stats/notifier/stats_notifier.dart:14`, `lib/features/stats/data/stats_repository.dart:8`.

**Изменение:** отдельные блоки подписки и текущего соединения; неотрицательный отображаемый остаток; корректные missing/unlimited/expired состояния; unavailable отличается от подтверждённого нуля. Новая тяжёлая модель данных не нужна: использовать существующие сигналы, а небольшую адаптацию представления добавлять только там, где они не выполняют контракт.

### 3. Обновление подписки может переподключать VPN

У `UpdateProfileNotifier.updateProfile()` есть вызов reconnect для активного профиля. Вызвать его при каждом открытии кабинета — не безобидная синхронизация показателя.

Источник: `lib/features/profile/notifier/profile_notifier.dart:155`.

**Изменение:** чтение кабинета через пользовательский API отделено от обновления VPN-конфигурации. Первое должно работать без reconnect; второе сохраняет существующую семантику Hiddify и объясняет возможный перерыв. Наличие подходящего API требуется проверить в D0.1; отсутствие такого API не скрывается вызовом обновления профиля.

### 4. Скорость уже есть, но это не новый speed test

Hiddify получает uplink/downlink и отображает их готовыми форматтерами. В нём также есть отдельный speed test. Открытие кабинета не должно запускать этот тест, расходовать трафик или называть текущую активность максимальной скоростью тарифа.

Источники: `lib/features/stats/widget/side_bar_stats_overview.dart:72`, `lib/utils/number_formatters.dart:6`, `lib/features/proxy/overview/proxies_overview_notifier.dart:332`.

**Изменение:** две строки текущей скорости; существующие байты/с и единицы объёма подписываются корректно. Тест скорости — только необязательная будущая ссылка на существующее действие. Историю графиков и счётчик «за месяц» не добавлять в первую версию.

### 5. Готовый simulator runner требует небольшой адаптации к CI

Runner уже умеет visual и write/read режимы, но содержит абсолютные локальные пути Flutter и pub-cache. Его нельзя объявлять готовой переносимой CI-командой.

Источник: `scripts/blizzard_simulator_run.py:16`, `:27`, `:36`. Существующий workflow: `.github/workflows/baseline-telemetry.yml`.

**Изменение:** адаптировать этот runner и расширить существующий workflow; не создавать новый тестовый фреймворк. Полный финальный native прогон — обязательная приёмка новой основы; короткий smoke — регулярная автоматизация. Отрицательные archive fixtures подключить из уже существующего набора.

### 6. Имя shortcuts не доказывает поддержку iOS Shortcuts

`ShortcutWrapper` содержит Flutter keyboard/TV actions, а не готовые App Intents или виджет iOS. В первоначальном плане формулировка «модуль shortcuts в общей базе» могла создать ложное ожидание дешёвого переноса.

Источник: `lib/features/shortcut/shortcut_wrapper.dart:22`.

**Изменение:** явно отмечена платформенная граница. Виджет/iOS shortcuts остаются дальнейшей гипотезой с отдельной оценкой.

## Что полезного добавить без большого расширения

- **Свежесть данных:** «Данные получены …» для ответа API и отдельно «Профиль обновлён …», если подписка импортирована. При ошибке сохранять прежние значения с датой только в рамках той же сессии аккаунта и подписки; время получения не выдавать за время расчёта расхода провайдером.
- **Ясный остаток и срок:** конечная квота, исчерпание, отсутствие сведений, истечение и нормализованный неограниченный лимит различаются. Процентная шкала нужна только для известного конечного лимита.
- **Принадлежность данных:** видны аккаунт и подписка; связанный профиль показывается после импорта. Серверные показатели доступны и до импорта, отсутствие локального `subInfo` их не скрывает. Скорость отображается только для соответствующего активного подключения; частичный сбой статистики не скрывает подписку.

После этого можно рассмотреть существующий speed test и ссылки провайдера, если они нужны пользователю и подтверждены на целевой платформе. Дата сброса, устройства/HWID, история платежей и обещанная тарифная скорость требуют своих источников — из текущей квоты их вывести нельзя.

## Проверка результата ревью

Три разбора: польза/UX, инженерная стоимость/QA, архитектура и границы данных кабинета. Существенные выводы перепроверены по исходникам; план исправлен. Проверены статус PR и отсутствие diff между HEAD и merge commit. После ревью пользователь выбрал email/Telegram с получением подписки; этот выбор внесён в план и не требует повторного согласования. Фактическая готовность backend и нативного возврата остаётся задачей проверки, а не заявленным результатом.
